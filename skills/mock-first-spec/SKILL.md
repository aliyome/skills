# モック先行要件定義 (Mock First Spec)

文章で要件を固める前に、画面で認識のズレを暴く。AIによって実物水準のモック作成コストは激減した。依然として高コストなのは人間の「意思決定」である。安価なモックを先に作り、曖昧な文章ではなく目に見える画面の上に意思決定を乗せる。

## プロセス

### 1. 作り直しになるデータ分岐だけを絞り込む

文言、配色、レイアウト、配置場所はまだ一切議論しない。それらは画面を見ながら決める方が速い。
ここでは、後から変更するとテーブル設計やデータ構造から作り直しになる分岐のみを特定する。

決裁者への質問は、番号付きで、`yes` / `no` または二者択一で即答できる形にして最大1〜2問に絞る（例:「回答形式は単一選択のみか、自由記述やスケールも必要か」「非エンジニアが質問を編集できる管理画面が必要か」）。

ユーザーにこの質問を投げ、回答が得られるまで先へ進まない。

**完了基準**: データ構造に直結する1〜2個の二値質問を提示し、回答が確定していること。

### 2. 既存のデザイントークンとスタイルを調査する

対象コードベースを調査する:
- デザイントークン、CSS変数、Tailwind設定、テーマ定義
- 既存のレイアウト構造、ナビゲーション、ボタン、フォーム部品
- タイポグラフィ、カラーパレット、余白の規約

プロダクト実物のトークンを忠実に再現する。ハリボテ感のあるワイヤーフレームは見せかけの合意を生み、「まあイメージだから」と細部の違和感や仕様漏れが見過ごされる原因になる。

**完了基準**: 実プロダクトのCSS変数・カラー・コンポーネントが特定されていること。

### 3. 単一縦長HTMLモックを生成する

全画面を**1枚の自己完結型HTMLファイル**にまとめ、上から下へスクロールして通しで仕様が理解できる構成にする。

モックの構成順序:
1. **ユーザー画面**: 主要導線、モーダル、表示トリガー、操作時の状態。
2. **入力バリエーション**: サポートする全質問/入力形式とエッジ状態。
3. **管理画面**: 一覧画面、作成/編集フォーム、回答一覧/CSVエクスポート。
4. **決定事項と未確定事項**: ページの最下部に専用セクションを配置する:
   - **決まったこと**: 合意済みの仕様。
   - **決めたいこと**: 保留中の論点と「誰が決めるか（担当者）」。

モックはプロジェクト内のパス（例: `docs/mocks/<機能名>-mock.html` やワークスペース直下）に作成する。フィードバックを受けて更新する際は別ファイルを作らず、**同じファイルパスを上書き**して常に最新の合意状態を保つ。

**完了基準**: デザイントークンを適用した単一縦長HTMLモックが生成され、ユーザー画面・管理画面・末尾の合意セクションが揃っていること。

### 4. 画面を通じて誤解をあぶり出す

生成したモックのパスをユーザーに提示する。ステークホルダーと一緒に実画面を確認してもらい、以下のあぶり出しを行う:
- 会話では素通りしていた不要なUI部品
- 仕様の構造的な誤解（例: 複数種類の質問を作るのではなく、同一の質問セットを利用の節目ごとに複数回出す、等）
- 業務フローにおける導線の抜け漏れ

モック上で視覚的な合意が得られるまで、詳細な要件書の執筆やデータベース実装に進んではならない。

**完了基準**: 画面を通じて誤解や違和感を拾い上げるためのレビュー依頼がユーザーに提示されていること。
