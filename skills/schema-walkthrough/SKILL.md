# DBの歩き方 (Schema Walkthrough)

ER図は静的な構造を示すが、構造だけでは設計の妥当性を判断できない。妥当性の判断に必要なのは**動き**である。

架空のユーザーの利用タイムラインに沿ってテーブルに何がどう入るかを追い、画面項目とカラムを対照させ、ライフサイクルの変化に耐えられるかを検証する。

## プロセス

### 1. 時系列の行diffを作成する (見方01: いつ行が増えるか)

架空のアクター（例:「佐藤さんが管理画面でアンケートを作成」「田中さんが3件目の案件を開いて回答」）の時系列シナリオを作成する。

各ステップで以下を記述する:
1. 影響を受けるテーブルの行追加・変更を diff 風に表現する (`+ id: ...`, `~ status: ...`)。
2. 設計意図の注記を添える（例: なぜ回答前にインプレッションを記録するのか、なぜ質問と選択肢を分けるのか）。
3. **【必須要件】「何も起きないステップ」を必ず1つ以上含める**（例:「翌日、田中さんが同じ画面を開いた → 何も増えない、回答済みのため非表示」）。これにより、重複防止や冪等性の制御ロジックを証明する。

**完了基準**: 関係する全テーブルの行追加/更新diffと、明示的な「何も起きないステップ」を含む時系列シナリオが作成されていること。

### 2. 画面とカラムの全対照表を作成する (見方02: 画面のどこから来るか)

モック/画面に表示されるすべてのUI要素と、対応するDBカラムの2列対照表を作成する:

| 画面に出るもの | どこから来るか (`table.column`) |
| :--- | :--- |
| アンケート名 | `polls.name` |
| 質問文 | `poll_questions.text` |
| ... | ... |

対照表を監査する:
- カラムが割り当てられない画面項目がある ＝ **設計漏れ**
- どの画面にもバックグラウンド処理にも使われないカラムがある ＝ **不要なカラム**

**完了基準**: モックの全項目がテーブル・カラムと1対1で突き合わされ、過不足がゼロであること。

### 3. エッジケースと破壊的変更を検証する (見方03: 変えたら何が壊れるか)

データの変更・削除・通信障害シナリオを通じて、制約とスナップショットの妥当性を検証する:

1. **公開後の質問誤字修正**: 作成者が質問文を修正したとき、過去の回答データは当時の質問文（`asked_question_text` スナップショット）を維持できるか？
2. **選択肢の削除**: 選択肢が論理削除されたとき、過去の回答集計（`selected_choice_label` スナップショット）が壊れないか？
3. **二重送信・通信切断**: ユニーク複合制約（`poll_id, user_id` など）によって重複登録が弾かれるか？
4. **途中離脱・画面リロード**: 未回答のまま5回リロードされても、表示ログの重複制約が機能するか？
5. **親レコードの削除制限**: 回答が存在するアンケートを削除できないよう制御されているか？（下書きのみ削除可能など）。

**完了基準**: 5つ以上のシナリオについて、スナップショット、外部キー制約、整合性ルールが検証されていること。

### 4. レビュー用「5つの質問」を添える

チームレビューを導くために、ドキュメント末尾に以下の5つの問いを配置する:
1. このテーブルは、誰が何をしたときに行が増えますか？
2. 画面のこの項目は、どのカラムから来ますか？
3. この重複防止ルールが無いと、何が起きますか？
4. このカラムは、どういうときに空（NULL）になりますか？
5. 元の情報を後から変えたら、過去のデータはどうなりますか？

作成したレビュー資料は `docs/db/<機能名>-schema-walkthrough.md` に保存し、マイグレーション作成前のチーム合意に用いる。

**完了基準**: レビュー資料がファイルとして保存され、スキーマ合意の準備が整っていること。
